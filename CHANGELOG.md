## 2026-09-13 — A delegation without a scope is now unwritable (`SIGNOFF-REPAIR.3.4.1.1`)

That held for production and NOT for the test suite.** `tests/authority.rs` constructed a delegate with no scope in two places, so the widening gate was being skipped inside a test that reads as though it exercises delegation. The audited-delegation test keeps `TenantWide`, matching the subject's own grant selector, so it still asserts the allow it always asserted — now through the gate instead of around it.

## 2026-09-13 — The cache's freshness window compared two different clocks (`SIGNOFF-REPAIR.3.4.3`)

- The leaf asked what a cached decision dated in the future means. Tracing the clock answered it: `decided_at` is the **server's database clock** (`database_now_in_tx`, and `tx.database_now()` on the replay path — the only two writers, and no request field reaches either), while the freshness comparison runs against the **node's process clock**. A future `decided_at` is therefore backward node skew and nothing else.
- 🔴 The consequence, stated as the bound it is: with the node behind by `S`, a cached allow stood for `S + 60 s` of observed time instead of 60 s.
- **That window is load-bearing, which is what makes the stretch matter.** The revocation epoch is bumped in exactly two places, both explicit revocations; a grant that simply reaches its own `expires_at` bumps nothing. So natural grant expiry is bounded at the node by the freshness TTL **alone**, and a stretched window is a stretched authorization window.
- ⛔ Both options the leaf was opened with were rejected by that measurement. Refusing a future instant refuses the server's own clock and turns skew into an outage; documenting it and moving on publishes a 60 s bound the product does not honour.
- The window now runs from `min(decided_at, received_at)` — the node's own receipt, already in its journal. It binds **iff** the node received a decision before its clock says the server made it, is byte-for-byte the shipped behaviour for any ordinary receipt, and can never refuse work the plain rule allowed: the window always ends at least one TTL after receipt.
- ⚠️ **The opposite skew direction is deliberately unchanged.** A node clock running *ahead* refuses every dispatch past 60 s of skew — fail-closed, journaled, safe. Backward skew failed *open*. Fixing only the fail-open direction is the correct scope; the availability defect is now owned by `.3.4.3.1`, along with whether the wire should carry a duration instead of an instant.
- 🔴 The clamp introduced a hazard the shipped suite does **not** catch: a replay rewrites `decided_at` on a row the journal already holds, so anchoring it to the ORIGINAL receipt would make a command replayed days later stale on arrival. The existing replay control passes either way because it seeds and replays within milliseconds. The receipt is refreshed with the decision, guarded on the decision having actually changed — every poll re-records every delivered command, so an unguarded refresh would re-anchor the window one poll at a time.
- Validation: `cargo test -p reasonbraid-core -p reasonbraid-node` over the affected set rc=0 — **10 targets, 116 tests, zero failures**. Five new controls; the five pre-existing cached-decision controls and the always-standing-deny unit test pass unchanged. Strict lint on both crates, fmt, gate (17 checks), book and link check rc=0.
- FALSIFIED three times, each reversion isolating one part: no clamp → both skew controls fail with the dispatch allowed; no receipt refresh → only the replay control fails, `expires 2026-09-11` against `decided 2026-09-13`; no guard → only the redelivery control fails.
- ⛔ Not claimed: the node journal is not a boundary and this does not make it one. Skew is now bounded, not **detected** — nothing reports that a node's clock disagrees with the server's.

## 2026-09-13 — A revoked delegation was told it had succeeded (`SIGNOFF-REPAIR.3.4.2`)

- 🔴 Measured on the unchanged path: a first request delegating to a LIVE role answered `200`; a second with the **same key and body** delegating to a **REVOKED** role answered `200 replayed=true` with `ok: true` — and wrote **zero** authorization records. - Root cause: `request_hash` covered the operation, the actor and `envelope.body`, and `authority_context` is a SIBLING of `body`, not part of it. The idempotency claim is step 1 of the command transaction and authorization is step 2, so a matching hash returns the stored result — success or stored refusal — without evaluating the second request's authority at all.
- ⛔ **No new effect is applied by such a replay**, so this was never an escalation of what was written. What it was: an unauthorized request answered with a success, invisible to the audit. Both halves are stated rather than the scarier one alone.
- The hash now takes the authority context and appends it when present. It is `409 idempotency_mismatch` — the same key describing a different request.
- ⚠️ **The migration answer was chosen, not assumed.** The hash is a STORED value, so changing its inputs is a wire change. A request with no authority context hashes **byte-identically** to before, because the suffix is appended only when there is one, so every historical undelegated key keeps replaying — nearly all of them. A historical *delegated* key now conflicts instead of replaying: the safe direction, since it refuses rather than returning a result decided under a different authority.
- The control asserts both halves in one test: the changed context conflicts, AND a genuine replay — same key, body and subject — still returns the original result marked `replayed`. A binding that worked by breaking replay would fail it.

## 2026-09-13 — The delegation and cache surface, censused and split (`SIGNOFF-REPAIR.3.4`)

- The leaf's own goal line named four mechanisms — delegability, bounded depth, replay-hash binding, cache freshness — plus two inherited representation follow-ups. Split into five children before implementing, as `.10` and `.11` were, with the census command recorded so it re-runs at any commit.
- 🔴 **`evaluate()` — the function that decides every command — never reads `grant.delegable`.** The flag is read in exactly one place, and only in the direction "a grant claiming to be delegable must sit under a delegable boundary". Nothing asks, when a request arrives on behalf of someone, whether that subject's grant permits being delegated at all. A grant issued with `delegable = false` backs a delegated request exactly as a delegable one does. `.3.4.1` owns it.
- 🔴 **The replay hash does not bind the authority context.** `request_hash` hashes the operation, the ACTOR's identity and `envelope.body` — and `authority_context` is a sibling of `body`, not part of it. Two requests identical except for `on_behalf_of` therefore produce the same idempotency key, and the second replays the first's stored result without its own authority ever being evaluated. `.3.4.2` owns it, starting by measuring whether the store holds denials, which decides whether this is only an audit defect or also a refusal that can be replayed away.
- **Bounded depth is deliberately not enforced, which is not the same as missing**: `let _ = boundary.max_delegation_depth; // dev profile: only direct grants exist; chains are Phase 2`. A depth bound with no chains to bound is machinery without a population, so `.3.4.1` owns saying so in the book rather than repairing it.
- **A structural hazard that is NOT reachable today, recorded so it is not rediscovered as a defect**: the §16.3 widening check sits inside `if let Some(scope)`, so a `CommandAuthz` with a delegate and no scope would delegate with the subject's full selector. The only caller that sets a delegate always sets the scope too. `.3.4.1` owns making the pair unconstructible rather than merely unused.
- ⭐ **The cache's two halves fail in opposite directions.** `is_invalidated` uses `!=`, so a decision claiming a FUTURE epoch reads as stale and fails safe. `is_fresh` is `now < expires_at` and never reads `decided_at`, so a decision claiming to have been decided in the future is fresh for its whole stated window. `.3.4.3` owns deciding it — and the leaf notes that where the clock comes from settles it: if `decided_at` is server-produced, refusing a future value turns clock skew into an outage; if a node can influence it, refusing is the only safe answer.
- Task-tree and index only: no production source changed, and no repair is claimed. The frontier advances to `.3.4.1`.

## 2026-09-12 — Revocation becomes one transaction, from the admission to the evidence (`SIGNOFF-REPAIR.3.3.4.8`)

- Grant and boundary revocation ran **two** guarded transactions: the handler admitted the caller under a SHARED guard, then a service opened a second one under an EXCLUSIVE guard. Between them the admission could be a fact about authority that had already stopped holding, and the submitted reason and the final outcome were never recorded with the mutation at all.
- Both routes now run ONE transaction under the tenant's exclusive guard, holding database time sampled after the guard wait, the admission on that same connection, tenant-bound `FOR UPDATE` target selection, the status change, the revocation-epoch bump, and the final effect record. This is the first route to produce the evidence `.7` defined.
- ⛔ **The superseded services are deleted, not deprecated.** A second guarded transaction able to revoke the same rows without an admission is exactly the hazard this closes, and `.3.3.4.3.4` already established that a migrated bridge gets removed.
- Every answer, refusals included, now carries `x-reasonbraid-authorization` naming the admission — which is also the effect record's id when one was written. Without it the effect record would be unreachable: there is no list endpoint.
- What commits an effect is narrower than what commits an admission: a 403 denial and a 400 malformed reason record their admission only, because the request never became an operation. A 404 DOES record `refused`/`not_found`, in the caller's own tenant, naming only the id the caller supplied — so missing and foreign stay one indistinguishable answer, preserving `SIGNOFF-REPAIR.3.1`.
- Two documented wire changes: the submitted reason gains the 1 024-byte, control-character-free contract site authority already publishes (exactly at the ceiling succeeds, one byte over is 400 before any effect is recorded), and `revoked_at` is now the transaction's own database time rather than a process clock read afterwards.
- Validation: `bash scripts/run_pg_tests.sh administrative_effects` returns rc=0 — **16 passed / 0 failed**, confirmed on three independent runs, clusters removed. FALSIFIED **11 passed / 5 failed** against two attributable injections: restoring the pre-`.8` shape makes `authority_that_ends_while_a_revocation_waits_refuses_it` report `left: 200, right: 403` — the revocation APPLIES after the caller's administration ended while it queued — and suppressing the effect write fails the other four. Eleven controls passed at that baseline, so the negative build was weakened rather than broken.
- ⚠️ One control's own expectation was wrong and the control caught it: it asserted the epoch was 1 after a raw `UPDATE` ended the caller's authority. That UPDATE is SQL, not the application, so it bumps nothing — 0 is both correct and the stronger claim, since any advance could only have come from the blocked request.

## 2026-09-12 — The stored refusal code named the wrong vocabulary (`SIGNOFF-REPAIR.3.3.4.7.3`)

- ⚠️ **This is the sixth instance of `.11.6`'s pattern and it is mine** — a vocabulary reasoned carefully from source without measuring the population it had to cover. The reasoning was sound and the set was wrong, and only building the first consumer exposed it.
- ⭐ **The obvious fix was rejected by a census, again.** "Add `NotFound` to the registry" assumes the gap is one value. ## 2026-09-12 — Store the final administrative effect with the mutation it describes (`SIGNOFF-REPAIR.3.3.4.7.2`)

- `.7.1` defined the effect representation and it had nowhere to live: `git grep -n "administrative_effects" -- migrations/ crates/*/src/` returned nothing. An operator could read an admission's `allowed` and had no row anywhere saying what the local mutation then did.
- Migration 0058 adds `administrative_effects`, keyed by **the admission's own `authz_…` id**, so there is at most one effect per admitted request and an effect with no admission is unrepresentable. It is additive in the strict sense: no existing table, column, constraint or row changes, and nothing is backfilled — an unrecorded outcome is not a recoverable one.
- ⭐ **Each invariant is placed where it can actually hold, not where it is easiest to write.** The operation/target pair is unrepresentable-if-wrong in the TYPE; "an effect belongs to its admission's tenant" is a COMPOSITE foreign key `(record_id, tenant_id)` rather than a convention the writer is trusted to follow; the `kind` discriminant is a column `CHECK`; and only what neither can express is left to the codec. A decoder check runs on the way OUT, after the bad row already existed, which for evidence is the whole problem.
- `record_administrative_effect_in_tx` takes the caller's **already-guarded** connection and takes no guard of its own — that would be a second acquisition on a connection that already has one. Sharing the transaction is what makes evidence and mutation one commit, and what makes an evidence failure roll the protected write back. `load_tenant_administrative_effect` filters by tenant **before** decoding, so a foreign malformed row is absent rather than an existence oracle.

## 2026-09-12 — The closed typed administrative effect representation (`SIGNOFF-REPAIR.3.3.4.7.1`)

- An admission record says a caller **was allowed to ask**. It says nothing about what the local mutation then did, so an operator reading `allowed` as `applied` is reading something the record never claimed. `docs/decisions/2026-09-09_tenant-authority-transaction-order.md` specified an additive final-effect record for exactly that gap and asked `.7` to define its representation before `.8` converts grant/boundary revocation onto it.
- `reasonbraid-core` gains `AdministrativeEffectRecord`, `AdministrativeOperation`, `AdministrativeOutcome`, `AdministrativeReason`, `AdministrativeTargetId` and `AdministrativeTextError`. No schema, no server change, and **no route writes one yet** — this is a primitive, qualified the way `.3.3.4.2` qualified the tenant guard before any application used it.
- ⭐ **The closed operation set was MEASURED, not chosen.** A closed enum is a rule over a population, and `.11.6` records five occasions where a rule reasoned carefully from source was changed by the first measurement of what it quantified over. The census enumerates all **27** guarded-admission call sites in `api.rs` and classifies every one: 9 reads, 18 mutations, of which **14** are owned by this family's `.8`–`.12` children and **4** are routed elsewhere (`register_resolver` → `SIGNOFF-REPAIR.7.1` — the top-level family, not this leaf — and `create_thread_auto`/`open_recruitment_call`/`close_call` → `SIGNOFF-REPAIR.5.2`). The 14 reproduce those four children's own declared scopes exactly, 2+2+5+2+3, which is a cross-check the set would have failed if it had been invented.
- Operation and target are ONE closed type, so a target that cannot belong to its operation is unrepresentable rather than merely discouraged, and there is no second enum to keep in step. Every target is something the CALLER supplied, so it exists at refusal as well as at success — which is why a card import names the card's digest rather than the local role it has not created yet, and why breaker administration names no target at all: its target is the tenant the record already carries.
- The record's identity IS its admission's `authz_…` id. `docs/CLAIM_VERIFICATION.md` leg 3 prefers one derived source over N synchronized copies; here it also means an effect with no admission is not a thing the model can represent.
- Outcome is closed: `applied` asserts a protected change, `no_op` and `refused` both assert that protected state and the revocation epoch are unchanged. A refusal names a `KnownReasonCode` from the existing §9.8 registry, so the record and the request's own response cannot disagree; a code outside that registry is a decode **failure**, never a guessed outcome.
- ⚠️ **`Option<T>` does not make a serde field required, and the control caught it.** The first draft documented `submitted_reason` as explicit, and serde's missing-field path answers `visit_none` for an `Option` — so a writer that dropped the member would have read back as "no reason was submitted". The control failed on that draft; a `deserialize_with` field has no such fallback, and the member must now be present, `null` when the operation takes no reason.
- Validation: 10 new representation controls; `cargo test -p reasonbraid-core` **68 passed / 0 failed** (51 unit + 10 + 4 + 3; 1 pre-existing ignored). - Explicitly NOT claimed: no migration, no writer, no reader and no route. `.7.2` owns the schema, the guarded writer and the exact own-tenant readback; `.8` is the first producer.

## 2026-09-12 — Guard the standalone read admissions before they select their evidence (`SIGNOFF-REPAIR.3.3.4.6`)

- The eight frozen-tenant reads do not merely return data: each COMMITS an admission record that NAMES the selected parent's status and the grant's selector. Unordered, that evidence can be read either side of the writer that changes it, and the record is what an operator later trusts.

Enumerating all **28** guarded-admission call sites and checking each enclosing function for a preceding `pool.begin()`, `transact(` or `TenantTransaction` found **0** — they are handlers that admit first and act afterwards.
