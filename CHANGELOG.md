## 2026-09-20 — The tail read is the offer, and the instant it writes does not move (`SIGNOFF-REPAIR.11.24.1.1.1`)

`REASONBRAID-REPAIR-0308`. §10.6's `offered` ships; `acknowledged` is deferred with a measured trigger.

- 🔴 **`offered` had no producer, so a row the server had handed to a transport read `queued`** — the same answer as a row it had never tried to deliver. Those are two different faults: rows stuck at `queued` say the node is not polling, and rows reaching `offered` and stopping there say it is polling and the responses are not arriving. The surface an operator reads could not tell them apart.
- ✅ **The producer is the tail read itself, because that is where the fact exists.** `replay` is the one function the handshake and the poll both read the tail through, and the rows it returns are the rows a response carries. The mark rides the **same statement** as the read, as a data-modifying CTE — two statements would be two snapshots, and the pair is not in a transaction, so a row could enter the tail between them and be delivered unmarked. ⛔ **A withheld row is not marked**: the mark is scoped to the rows the tail returns, so quarantine and an ended authority exclude a row from the offer exactly as they exclude it from the response.
- ⭐ **`offered_at` is written once, and that is derived rather than preferred.** The leaf asked whether a re-offer should bump the instant or preserve the first; a window measures time in the state being retained, so an instant a re-offer bumps silently resets every age measured from it — a node polling in a loop would keep its oldest outstanding work looking new.
- ⛔ **The offer count is refused**: the question the state exists to answer is answered by the state, and *a column is not missing until something needs it* is this tree's own rule. Trigger stated — a reader that must tell one offer from forty. ⛔ **The backfill is refused twice over**: a delivered row outranks `offered` so dating it changes nothing observable, while `acknowledged_at` is provably later than the real offer; and a `queued` row, the case where it would matter, has nothing to derive from. A migration control drives the absence, because a decision nothing exercises is indistinguishable from an oversight.
- ⚠️ **`acknowledged` is deferred on a measurement, not an assumption.** §10.6 defines it as the state whose acknowledgement semantics are *explicit per event type*, and the channel has one cursor ack covering every row whatever their types. The dispatch has exactly two kinds today — `contribute` and `revise` — and confirmation means the same thing for both, so the per-type contract has nothing to distinguish. Trigger: a command kind whose acknowledgement means something different from a work item's.
- 🔎 **A hazard the suite caught before a reviewer could.** `node_inbox_state` is `SELECT i.*, … AS delivery_state`; the star expanded positionally at creation, so the new column lands ahead of `delivery_state` and `CREATE OR REPLACE VIEW` may only append — PostgreSQL refuses with `42P16` and every migrating suite fails at once. `0078` drops and recreates, and the standing hazard is recorded rather than gated: the schema has two views and this is the only one that expands a star. ⭐ It is the other half of `SIGNOFF-REPAIR.13.4.3.1`, two commits earlier — applying a migration proves its SQL *runs*, which caught this instantly; only a driver catches what it *means*.
- 🔎 **What `offered` now makes possible is owned, not noted:** `.11.24.1.1.2.1` narrowed the cursor ack to exclude rows the tail withheld and recorded its own residual — a row offered and then quarantined goes unmarked and is re-delivered. The recorded offer is the fact that residual was missing. Owned at `.11.24.1.1.1.1`, with the pre-`0078` NULL cohort named as the hazard that leaf must answer rather than discover.
- ✅ **VERIFIED:** `node_inbox` 10 (9 before), `node_work` 12, `node_channel` 40, `migration_upgrade` 7 (6 before), `mcp_listen` 6 — **75 passed / 0 failed**, owned cluster stopped and removed. No existing `delivery_state` assertion moved, which is the view precedence holding. Strict focused clippy rc=0; `cargo fmt --all --check` rc=0; `make book` rc=0; doctrine gate green. **FALSIFIED four ways, each file restored byte-identical**: the mark removed, its write-once guard removed, the mark unscoped from the tail, and the rung removed from the view each turn the control red.

## 2026-09-20 — An expired row prunes on its own window, and a revoked one has no clock to prune by (`SIGNOFF-REPAIR.11.24.1.1.2.1.1`)

`REASONBRAID-REPAIR-0302`. The retention answer for the two terminals the previous two commits created.

- 🔴 **A row in §10.6's `expired` or `revoked` was never delivered, so it carries no `acknowledged_at` — and `POST /v1/nodes/inbox/prune` deletes on exactly that.** Between `.11.24.1.1.2` giving a queued command a terminal and `.11.24.1.1.2.1` stopping the cursor acknowledgement writing a receipt it had not earned, no operator verb could remove one. ⛔ **Solving *held forever* for delivery and recreating it for storage is not a repair.**
- ⭐ **The rule this rests on: a retention window measures time in the state being retained.** An operator asking to delete rows older than seven days is saying how long they want to be able to *see* a finished row, not when it happened to be created. Ageing by anything else silently deletes rows they expected to still be there.
- 🔴 **And the rule does not give the same answer twice, which is the whole decision.** `expired` has an exact entry instant — the admitting grant's `expires_at` — so its window is `g.expires_at <= cutoff` and measures precisely time-in-terminal. `revoked` has none: `authority/revocation.rs` writes `SET status = 'revoked'` and `authority_grants` carries no `revoked_at`. `node_inbox.decided_at` exists and would age the row, so the obstacle is not a missing column — it records when the row was *created*, a different quantity, and a command queued thirty days ago under a grant revoked this morning would vanish under a seven-day window on the day it entered the terminal. So `expired` becomes prunable and `revoked` does not, with the trigger at `.11.24.1.1.2.1.1.1`.
- **The oracles, and where they pushed.** §12.9 — *deletion creates a tombstone and reason, not silent disappearance* — and §16.11's preservation of evidence through quarantine both lean towards retention, and they are why the answer is not simply to sweep the terminals. The prune is an explicit, authorized act that takes the tenant's guard, writes an effect record with its reason and returns a measured before/after, and a quarantined row is still never deleted.
- ⚠️ **`deleted` is now the total, with `deleted_delivered` and `deleted_expired` beside it.** Its meaning widened: it used to be reachable only by delivered rows, so a client reading it as *delivered rows removed* was accidentally right. The CLI moved with it in the same commit — *pruned N delivered row(s)* became *pruned N row(s) — M delivered, K expired undelivered* — and it was found by censusing the corpus for the receipt's field names rather than by remembering it, which is `.13.4`'s standing rule applied to a CLI surface.
- 🔴 **The first falsification found a real gap rather than confirming the design.** Removing `AND g.status = 'active'` left the revoked control green, because a revocation does not move `expires_at`, so a merely-revoked grant was excluded by the window alone and the clause was dead code. The control now ages the revoked grant past its expiry as well — the case where the two differ: the view calls that row `revoked` (the act outranks the lapse) and the prune must agree with the view rather than delete it as an expiry.
- ⭐ **The window arm runs before the deletion arm**, deliberately: a grant that expired two hours ago is *not* removed by a one-day window. Without that arm a passing deletion would prove only that the row can be destroyed, not that the operator's window governs when.

## 2026-09-20 — A cursor acknowledgement stops receipting rows the tail withheld (`SIGNOFF-REPAIR.11.24.1.1.2.1`)

`REASONBRAID-REPAIR-0301`. Reproduced as RED through the public surface before a line of the repair was written.

- 🔴 **`acknowledge` marks every row up to the acknowledged cursor** (`WHERE cursor <= $2`) while `replay` — the one function the handshake and the poll both read the tail through — withholds rows the node must not receive. The two predicates disagree, so a withheld row gains an `acknowledged_at` the moment the node acknowledges a later row it really did receive, and `migrations/0075` defines that column as *the node process durably holds this command*. Quarantine row 2 of three, let the tail hand the node rows 1 and 3, acknowledge cursor 3: row 2 carries the receipt. The node cannot acknowledge around the hole, so this is the ordinary path rather than a contrived acknowledgement.
- ⛔ **Not a cosmetic column, and the harm model was already on the record.** `a_fenced_acknowledgement_cannot_mark_another_sessions_delivery` (`SIGNOFF-REPAIR.4.2.4`) states it for this exact shape: `acknowledged_at` is the retention prune's `DELETE` predicate, so a false receipt makes work that was never delivered eligible for deletion. The quarantine case is shielded by that predicate's own `quarantined_at IS NULL` — and `POST /v1/nodes/replay` clears the quarantine while leaving the false receipt behind, which takes the shield with it.
