## 2026-09-13 — The stored certificate expiry was never read from the certificate (`SIGNOFF-REPAIR.3.4.3.1.1`)

## 2026-09-13 — The cache's freshness window compared two different clocks (`SIGNOFF-REPAIR.3.4.3`)

- The leaf asked what a cached decision dated in the future means. Tracing the clock answered it: `decided_at` is the **server's database clock** (`database_now_in_tx`, and `tx.database_now()` on the replay path — the only two writers, and no request field reaches either), while the freshness comparison runs against the **node's process clock**. A future `decided_at` is therefore backward node skew and nothing else.
- 🔴 The consequence, stated as the bound it is: with the node behind by `S`, a cached allow stood for `S + 60 s` of observed time instead of 60 s.
- **That window is load-bearing, which is what makes the stretch matter.** The revocation epoch is bumped in exactly two places, both explicit revocations; a grant that simply reaches its own `expires_at` bumps nothing. So natural grant expiry is bounded at the node by the freshness TTL **alone**, and a stretched window is a stretched authorization window.
- ⛔ Both options the leaf was opened with were rejected by that measurement. Refusing a future instant refuses the server's own clock and turns skew into an outage; documenting it and moving on publishes a 60 s bound the product does not honour.
- The window now runs from `min(decided_at, received_at)` — the node's own receipt, already in its journal. It binds **iff** the node received a decision before its clock says the server made it, is byte-for-byte the shipped behaviour for any ordinary receipt, and can never refuse work the plain rule allowed: the window always ends at least one TTL after receipt.
- ⚠️ **The opposite skew direction is deliberately unchanged.** A node clock running *ahead* refuses every dispatch past 60 s of skew — fail-closed, journaled, safe. Backward skew failed *open*. Fixing only the fail-open direction is the correct scope; the availability defect is now owned by `.3.4.3.1`, along with whether the wire should carry a duration instead of an instant.
- 🔴 The clamp introduced a hazard the shipped suite does **not** catch: a replay rewrites `decided_at` on a row the journal already holds, so anchoring it to the ORIGINAL receipt would make a command replayed days later stale on arrival. The existing replay control passes either way because it seeds and replays within milliseconds. The receipt is refreshed with the decision, guarded on the decision having actually changed — every poll re-records every delivered command, so an unguarded refresh would re-anchor the window one poll at a time.
- Validation: `cargo test -p reasonbraid-core -p reasonbraid-node` over the affected set rc=0 — **10 targets, 116 tests, zero failures**. Two administrators attesting two different capabilities of the same role both read version N and each writes a profile carrying only its own upgrade; whichever commits second publishes a profile in which the first attestation never happened, with no error on either side. Serializing the writes does not fix it — the second writer's version number is correct while its content is stale — so the read must move under the same lock as the write.
- 🔴 **The import commits the identity and writes the profile afterwards.** The grant, `agent_roles` row, quota row, enrollment row and cross-domain receipt commit as one transaction; the profile is then written on the pool. A failure there answers 500 with an orphan role, grant, quota, enrollment and receipt already durable and no profile behind them. The import also reads its admission, its active boundary and the effective agreement OUTSIDE the transaction that uses them, and the boundary is what the created grant is checked against — so a boundary revoked in between is a grant created against authority that has already ended.
- ⚠️ Measured, and it bounds what the import child may claim: `federation::revoke` is a bare pool `UPDATE` with no guard, as are `propose` and `accept`. Holding the origin tenant's guard would therefore NOT fence a concurrent agreement revocation. Moving the agreement read inside the transaction buys snapshot consistency with the writes and nothing more; that ordering arrives with `.3.3.4.12`.
- ⛔ Provenance stays where it is owned: `cards::verify_pure_rungs` proves the digest re-derives from the card, which is integrity, not provenance — the origin tenant is caller-asserted, and the bilateral recruitment agreement is what bounds the consequence. `.5.3` owns replay and provenance; no child here invents a provenance rule while moving a transaction.
- Three children, ordered by dependence: `.11.1` the transactional writer and the role/version anchor, `.11.2` the guarded attestation, `.11.3` the atomic import. Guard modes are deliberately NOT decided here — each child derives its own, as the `.8`/`.9`/`.10.1`/`.10.2`/`.10.3` sequence's exclusive/exclusive/shared/exclusive/shared answers required.
- Task-tree and index only: no production source changed, and no repair is claimed. The frontier advances to `.3.3.4.11.1`.

## 2026-09-12 — The inbox verbs were not bound to a tenant, and one of them deleted another tenant's rows (`SIGNOFF-REPAIR.3.3.4.10.3`)

- 🔴 `node_inbox` has carried a `tenant_id` column since migration 0003. **None of quarantine, replay or prune used it.** A probe run before this repair, with an administrator of tenant A acting through the supported HTTP surface on a node whose inbox rows belong to tenant B: quarantine answered **200** and quarantined the foreign row; replay answered **200** and un-quarantined and re-sequenced it; prune answered **200** with `{"deleted":2,"before":2,"after":0}` and **destroyed both of the other tenant's rows**. Reachable by any ordinary tenant administrator.
- ⚠️ **Three of this project's own fixtures depended on the defect, which is why nothing caught it.** `node_inbox.rs` seeded its node and rows into a fixed seed tenant and then administered them as an administrator of a different, freshly bootstrapped tenant. Applying the tenant binding turned all three red at once. They are CORRECTED rather than deleted — the helpers take the tenant, each test bootstraps its administrator first and seeds into that administrator's own tenant — and every original feature assertion is intact. The other three suites that drive these verbs needed no change, because their nodes already belonged to the administering tenant.
- All three verbs now run ONE transaction under the tenant's SHARED guard: the admission, a tenant-bound `FOR UPDATE` row selection, the mutation and the final effect record. A foreign target is now indistinguishable from an absent one and mutates nothing. The prune's `before`/`after` counts are bound too — an operator's receipt must describe the inbox they are allowed to see, not every row the node happens to hold.
- The mode is shared because none of the three writes authority or advances the revocation epoch; what they need is to be fenced BY a revocation, which shared gives. Exactness against a concurrent administrator comes from the row lock, at the granularity that actually conflicts.
- Three DISTINCT transaction bodies, on purpose: quarantine's check-then-update became one locked read and write; replay keeps exactly the two decision facts it refreshed (`SIGNOFF-REPAIR.3.4` still owns WHICH); prune keeps its measured receipt and the §16.11 rule that a quarantined row is never deleted.
- Wire changes, documented and tested: the quarantine reason gains the 1 024-byte control-character-free contract and is persisted with the effect as well as on the row; `quarantined_at`, `replayed_at` and `cutoff_at` are the transaction's own database time; every answer carries `x-reasonbraid-authorization`. One message is RETIRED — a replay that lost a concurrent race used to say so, and the row lock makes that state indistinguishable from any other command that is not dead-lettered.
- Validation: `bash scripts/run_pg_tests.sh node_inbox` rc=0 — **7 passed / 0 failed**. The affected set `node_inbox node_work quarantine node_replacement node_channel administrative_effects` rc=0 with **6 suites, 72 tests, zero failures**. Strict lint, fmt, gate and book rc=0.
- FALSIFIED against the exact pre-`.10.3` handlers: **3 passed / 4 failed**. The foreign-administrator control fails `left: 200, right: 400` with the other tenant's row carrying a fresh `quarantined_at`, and the evidence-rollback control fails `left: 200, right: 500` with `{"deleted":2,"before":2,"after":0}` — the prune destroyed both rows AND reported success while its evidence could not be written.
- `SIGNOFF-REPAIR.3.3.4.10` closes with this: all five node administrative mutations its census found are now one guarded transaction with a tenant-bound target and a final effect record.

## 2026-09-12 — Node revocation becomes one transaction, with its reason kept (`SIGNOFF-REPAIR.3.3.4.10.2`)

- The route did its work in three pieces: an admission in its own transaction, a tenant-bound existence probe as a SEPARATE pool query, and then a third transaction whose `UPDATE node_certificates` matched on `node_id` alone. The check and the act read two different snapshots, nothing ordered either against an authority change, and no record said what the request finally did.
- It now runs ONE transaction under the tenant's EXCLUSIVE guard holding database time after the guard wait, the admission on that connection, the node row selected `FOR UPDATE` bound to the admitted tenant, the certificate revocation, the epoch bump and the final effect record.
- ⭐ **The mode is the opposite of `.10.1`'s, one commit earlier, and that is derivation rather than alternation.** This advances the tenant's revocation epoch, which invalidates every cached node-side admission decision — so it is a revocation in the sense the guard contract means, and `.8` established that a revocation takes the exclusive mode precisely so it fences admissions. A shared acquisition would have left the book's stated ordering false for one of the three writers that advance the epoch.
- The `UPDATE` now carries its own tenant predicate rather than trusting the probe that preceded it, so the binding is visible in the statement that actually writes rather than in one that ran earlier, elsewhere, against another snapshot.
- The single `409` still answers both idle states with the same message, and the effect record is where they stop being the same fact: every certificate already revoked is the request ALREADY SATISFIED and records `no_op`; a node that has never had a certificate records `refused`/`invalid_transition`. The query that distinguishes them runs on the refusal path only.
- Wire changes, documented and tested: the reason gains the 1 024-byte, control-character-free contract and is now **persisted** with the effect rather than checked for blankness and discarded; `revoked_at` is the transaction's own database time; every answer carries `x-reasonbraid-authorization`. Status codes, the 404/409 messages and the response fields are otherwise unchanged.
- Validation: `bash scripts/run_pg_tests.sh node_channel` rc=0 — **30 passed / 0 failed** (25 pre-existing plus 5 new), including both pre-existing revocation controls. The affected set `node_channel node_replacement node_enrollment administrative_effects command_ordering` rc=0 with **5 suites, 74 tests, zero failures**. Strict lint, fmt, gate and book rc=0.
- FALSIFIED against the exact pre-`.10.2` handler: **25 passed / 5 failed**, all five new controls. The discriminating one fails at `the revocation is waiting` — under the old shape the request COMPLETED while a shared holder held the tenant's guard, because the old admission took the shared mode and the mutation took no guard at all.
- ⚠️ The discriminating fixture is a SHARED holder here and was ATOMICITY for `.10.1`. Same parent, same sequence, two different correct fixtures — because this repair changed the lock mode and that one did not. Copying either would have produced a control that cannot fail.

## 2026-09-12 — Node enrollment-token issuance becomes one transaction (`SIGNOFF-REPAIR.3.3.4.10.1`)

- The route admitted the caller through `authorize_guarded` — its own transaction — and then inserted the token **on the connection pool**, outside any transaction, with nothing recording what the request finally did. It now runs ONE transaction under the tenant's SHARED authority guard holding database time after the guard wait, the admission on that connection, the token insert and the final effect record.
- ⭐ **The guard mode is derived, and it is a DIFFERENT answer from `.9`'s.** `.9` took the exclusive guard for two measured reasons, and neither holds here: there is no classify-then-write over a possibly-absent row, because one `INSERT … ON CONFLICT DO NOTHING RETURNING` decides `applied` against `refused` atomically; same-node contention is already serialized by migration 0018's partial unique index; and issuance touches nothing the reservation path reads. Shared mode still fences the whole request against an authority change, because a revocation takes the guard exclusively.
- ⛔ `ON CONFLICT DO NOTHING RETURNING` rather than catching the raised unique violation, for a structural reason: a constraint violation ABORTS the transaction and would take the admission and the effect record with it, so the established `409` could not be recorded as an outcome at all. Every later child with a uniqueness refusal needs this shape.
- Measured, and it narrowed what this child owns: `node_enrollment_tokens.node_id` has NO foreign key to `nodes`, deliberately — a token is issued before the node it names exists. So the tenant-bound target check the parent anticipated has nothing to bind to; the row is stamped with the admitted tenant, and lineage at redemption stays `.4.1`.
- Wire: status codes, the `409` message and the response fields are unchanged. Two documented additions — `x-reasonbraid-authorization` on every answer that reached an admission (the pre-admission validation refusal deliberately carries none, because no record exists to name), and `expires_at` now runs from the transaction's own database time plus the TTL rather than a process clock read before the guard wait.
- Validation: `bash scripts/run_pg_tests.sh node_enrollment` rc=0 — **11 passed / 0 failed**. The affected set `node_enrollment node_work node_replacement node_result_ordering profiles administrative_effects` rc=0 with **6 suites, 84 tests, zero failures**; the set is the five suites that issue a token, found with `grep -rln "enroll-tokens"`, plus the effect suite. Strict server lint, fmt, gate and book rc=0.
- FALSIFIED against the exact pre-`.10.1` handler restored from `HEAD`: **7 passed / 4 failed**. The discriminating control reports `left: 200, right: 500` — the token was ISSUED AND COMMITTED although its evidence could not be written.
- ⚠️ **A shared-guard repair cannot be falsified by a lock-holding fixture in either mode**, because the superseded admission took the shared guard too. What changed is atomicity, so the evidence-rollback control is the discriminating one and the ordering property is labelled a REGRESSION control in the suite rather than presented as proof of the repair.
- ⚠️ Reproduced while designing this and routed to `.3.5`, NOT introduced here: migration 0018's one-unused-token index is global rather than per tenant. Tenant A's administrator issues for node id N and gets 200; tenant B's administrator, issuing for the same N inside B's own tenant, gets 409 naming the outstanding token — an existence oracle for a known identity, and an availability hazard, since A can hold B out indefinitely. The probe was removed rather than committed as a control that would enshrine the defect.

## 2026-09-12 — The five node administrative routes, censused and split (`SIGNOFF-REPAIR.3.3.4.10`)

- The parent's own first act. Its children are drawn from a census of what the five handlers do rather than from their names, and the census command is recorded so it re-runs at any commit.
- ⚠️ **Four of the five mutations carry no tenant predicate at all.** `replay_command`, `quarantine_command` and `prune_node_inbox` select `node_inbox` rows by `node_id` (and `command_id`) alone; `revoke_node`'s `UPDATE node_certificates` matches `node_id` alone, its tenant-bound existence probe being a separate pool query outside the mutation's transaction and therefore check-then-act. Only `issue_node_enroll_token` names a tenant, and only as a column value stamped on the new row. The admission proves the caller administers tenant T; every one of the five then addresses a target it has not shown belongs to T.
- That finding's ownership is NOT moved: `.3.5` owns real target ownership and its foreign-node fixtures. This parent owns putting the verification INSIDE the mutating transaction, which is the half `.3.5` cannot do without the guard.
- Transaction shapes today: two of the five mutate on the pool with no transaction (quarantine as two separate statements) and three open their own transaction under no guard.
- Three children, along the three state machines rather than the five routes: `.10.1` token issuance, `.10.2` certificate revocation, `.10.3` inbox administration — carrying 1 + 1 + 3 of the five operations `.7.1`'s census assigned here.

## 2026-09-12 — Breaker administration becomes one transaction, from the admission to the evidence (`SIGNOFF-REPAIR.3.3.4.9`)

- Spend-breaker arm and reset were the **weakest** administrative path in the server, weaker than the shape `.8` replaced. Each admitted the caller through `authorize_tenant_admin` — its own transaction, SHARED guard — and then executed a bare statement **on the connection pool**: no transaction, no guard, and no record anywhere of what the operation finally did.
- Both verbs now run ONE transaction under the tenant's EXCLUSIVE guard, holding database time sampled after the guard wait, the admission on that same connection, tenant-bound `FOR UPDATE` selection of the breaker row, the mutation, and the final effect record. This is the second family onto the evidence `.7` defined.
- ⭐ **The exclusive mode is measured, not copied from `.8`.** Classifying `applied` against `no_op` is a read-then-write over a row that may NOT EXIST, and a row lock cannot cover an absent row. And the reservation path evaluates this latch inside thread-command transactions that hold the SHARED guard, so exclusive is what orders an arm against every in-flight reservation in the tenant — `budget.rs`'s own rule that the latch never lags the ledger it guards, now true of administration too.
- ⭐ **The outcome mapping came from a census of what the handlers actually do, run before it was written.** `git grep -n "spend_breakers" -- 'crates/*/src/*.rs'` returns five sites in two files; only two are administrative mutations. Reading their SQL against migration 0016 says `armed_at` is absent from the arm's `DO UPDATE` list, so re-arming the same threshold on an untripped breaker changes **no column at all** — recorded `no_op`, not `applied`, because `applied` asserts a protected change. And reset's `rows_affected() == 0` covers two different states that its message already admits to collapsing.
- **No wire change.** Request bodies, success bodies, status codes and messages are byte-unchanged. The one addition is `x-reasonbraid-authorization` on every answer, for `.8`'s reason: without it the effect record is unreachable, since there is no list endpoint. Neither verb takes a caller reason, so `submitted_reason` is `null` rather than a requirement invented here.
- The `409` that has always collapsed "no breaker armed" and "armed but untripped" still does; the effect record is where they stop being the same fact — `refused`/`invalid_transition` against `no_op`. It records `invalid_transition` rather than `not_found` because a breaker operation's target **is the tenant**, and the tenant was found.
- Neither verb advances the revocation epoch, in any outcome including the successful one — asserted in the controls, because that is exactly where a copied-from-`.8` mistake would show. The epoch invalidates cached authority decisions; a spend latch is not authority.
- `bounded_detail` MOVED from `revocation.rs` into `effects.rs` beside the record it bounds: two families now need it, and a second copy of the same fallback is the drift this tree keeps repairing.
- Validation: `bash scripts/run_pg_tests.sh administrative_effects` returns rc=0 — **25 passed / 0 failed** (the 16 from `.8` plus 9 new). The affected set `administrative_effects command_api budget authority command_ordering` returns rc=0 with **5 suites, 94 tests, zero failures**; clusters stopped and removed. Strict server lint, `cargo fmt --all -- --check` and `mdbook build` pass.
- FALSIFIED against the **exact** pre-`.9` handlers restored from `HEAD`: **17 passed / 8 failed**. Eight of the nine new controls go red; `a_breaker_request_waits_for_the_tenants_authority_guard_and_then_applies` fails at `breaker_row(...).is_none()` — the arm APPLIED while another operation held the tenant's authority guard — and `authority_that_ends_while_a_breaker_request_waits_refuses_it` reports `left: 200, right: 403`. Seventeen controls passed at that baseline, so the negative build was weakened rather than broken.
- ⚠️ **The falsification corrected the controls, not only the code, and the mistake generalises to `.10`–`.12`.** Both ordering controls were first written with an EXCLUSIVE holder, copied from `.8`, and were green — green against the unrepaired code too, because the superseded admission took a SHARED guard and therefore waited behind an exclusive holder exactly as the repair does. The discriminating fence is a SHARED holder: exclusive must wait behind it, shared walks straight through. Promoted to `docs/knowledge/proving-a-race-is-closed.md`.
- ⚠️ A second fixture defect: the evidence-rollback control installs a deliberate `CHECK (false) NOT VALID` and its first version asserted before dropping it; the leak failed the next eleven tests on a constraint unrelated to them. Repaired twice — the control now observes, drops, then asserts, and the suite fixture issues `DROP CONSTRAINT IF EXISTS` so a future leak costs one test instead of the suite.
